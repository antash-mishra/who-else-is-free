Part 1

The problem in one story

A notification is saved when something happens. The message remains in the inbox, but the thing it points to—an event, request, or chat—can later change or disappear.

1

Alice asks to join

The host receives: “Alice wants to join your Hike event.”

2

The notification is saved

It stores the event and chat numbers that existed at that moment.

3

The host deletes Hike

The event, request, and related chat disappear. The old notification remains.

4

The host taps the old row

The app trusts the old numbers and opens an empty or “not found” screen.

Think of it like an old invitation with a map. The invitation is useful history—it proves that the party was once planned. But if the party is cancelled, the map should no longer send you to an empty building. The message and the action are two different things.
Part 2

What the current plan proposes

The plan keeps notification text as history, while separately tracking whether tapping it is still useful. It uses two safety layers.

Layer A: Clean up early

When an event is deleted, a request is accepted or cancelled, or a member leaves, the server updates related notification actions immediately.

Purpose: keep the inbox and red badge clean.
+

Layer B: Check again when tapped

Just before navigation, the app asks the server where the user can safely go right now. The server checks current access and current data.

Purpose: catch races and missed cleanup.
1
Add action status. Each notification action becomes active, resolved, or unavailable.
2
Save better identifiers. New join-request notifications store the exact request number.
3
Update related notifications when data changes. Deleted events and completed requests stop looking actionable.
4
Add a server resolver. The app sends a notification number; the server returns a safe destination.
5
Use that resolver in the inbox and push notifications. Both entry points follow the same safety rules.
6
Restyle finished tasks. They become read, leave the unread badge, and remain as one muted Handled or Unavailable summary.
Why both layers? Early cleanup is like removing an outdated road sign. Tap-time checking is like GPS checking that the road is still open before sending you there. Either one can occasionally miss something; together they are reliable.
Part 3

What was corrected in the updated plan

These were gaps in the earlier version. The Markdown plan now includes each correction.

Correction 1

One visible row may represent several notifications

The app combines several requests for the same event into one row. The plan asks the server to check only one notification number, which may give the wrong answer for the whole group.

Example: Alice cancels her request, but Bob’s request is still waiting. Checking only Alice’s notification may say “nothing to do,” even though Bob still needs an answer.

Fix: send all notification numbers represented by the row and let the server check the group together.

Correction 2

Collapsed history can make a page look shorter

The server loads notifications in pages. Twenty finished notifications may collapse into one muted history summary even when more useful notifications exist on the next page.

It is like bundling the first 20 letters into one envelope: the app must still know that another page of letters exists.

Fix: keep the muted summary visible and base Load More on the raw server page, not on how many summaries are rendered.

Correction 3

The safest part is scheduled too late

The current phases add cleanup before tap-time checking. But tap-time checking is the final safety net and should exist before relying on cleanup hooks.

Fix: build the server resolver and inbox use earlier; add eager cleanup afterward.

Correction 4

Some push notifications will not have a saved ID

Saving notification history is intentionally “best effort.” A push can still be sent when saving its inbox row fails. That push therefore has no notification number to resolve.

Fix: permanently support a safe fallback that checks the event/chat identifiers and the signed-in user’s current access.

Correction 5

A replacement chat is not always the same destination

When an event changes between group and one-to-one, chats can be replaced. A message from an old chat should not automatically open a different new chat.

Fix: use rules per notification type. Requests can follow current event structure; old chat messages should validate their exact chat.

Correction 6

The database upgrade needs exact instructions

Existing installations already have a notifications table. Changing the “create table” text does not add columns to an existing database.

Fix: add an explicit, repeat-safe database migration and test both old and brand-new databases.

Correction 7

“Actor user ID” is vague

The plan proposes saving an actor user number without defining exactly who that means for every notification. It also complicates account deletion.

Fix: omit it for now. The exact join-request ID solves the known request problem.

Correction 8

There is no current automatic retention period

The plan says to keep the existing retention period, but notifications currently stay until the user clears them or deletes the account.

Fix: describe the current behavior honestly, or make automatic deletion a separate product decision.

Part 4

The simpler recommended order

This order installs the safety net first, then improves cleanliness and coverage.

Prepare the databaseAdd action status and exact join-request identity with a safe migration.
Build the resolverCheck ownership, existence, access, request status, and correct destination.
Use it in the inboxResolve single and grouped rows before navigation. Never navigate blindly.
Add early cleanupUpdate related actions when events, requests, memberships, or accounts change.
Cover OS push tapsUse saved IDs when present and a validated fallback when they are not.
Prove it worksTest races, mixed groups, pagination, legacy data, failures, and real-device flows.
Resolver rule

For a grouped row

Send every underlying notification ID. If any request in a request group is still pending, open Requests.

Database rule

For inbox pages and badges

Keep muted history in the list, exclude it from the unread count, and keep Load More available even when many raw rows collapse into one summary.

Failure rule

If the server cannot check

Stay on Notifications, show small retry feedback, and do not mark the row handled.

History rule

Keep the message, disable the dead action

Outcome messages remain. Inactive task groups become read, muted summaries with a Handled or Unavailable status and no unread dot.

Stale-row rule

Make stale status obvious

Automatically mark the row read, remove its unread dot, dim its presentation, and show an Unavailable icon and label. It remains tappable only for the safe fallback.

Explanation rule

Explain the Discover redirect

After Discover opens, show a one-time modal: “This event is no longer available. You can discover other events here.”

Part 5

What the user should experience

These defaults make the behavior predictable without bringing back a blocking access popup.

What is true now? What happens on tap? Why?
Request is still pending Open Requests There is still work for the host.
Request was accepted, denied, or cancelled; event still exists Open Event Details The task is finished, but the event is still meaningful.
Event was deleted Discover + event-unavailable modal There is no event page left, and the user deserves a clear explanation.
User lost membership or access Discover + generic unavailable modal The old private destination is no longer allowed, but the event may still exist.
Exact chat still exists and user is a member Open Chat The original destination is still valid.
Exact chat disappeared or was replaced Discover + generic unavailable modal Do not pretend a different chat is the original one; explain the fallback.
Server check temporarily fails Stay and retry Safety is more important than guessing.
Notification type is unknown Stay in Notifications Unknown data should fail safely.
Part 6

Small glossary

The technical words in the plan translated into everyday language.

Stale actionA button or tap destination that points to something that changed or disappeared.
Server-authoritativeThe server, which has current data and access rules, makes the final decision.
ResolverA server check that turns an old notification into a safe destination right now.
InvalidationMarking an old action as no longer usable.
Collapsed rowOne visible inbox row representing several saved notifications.
Race conditionData changes during the short time between loading the inbox and tapping a row.
PaginationLoading a long inbox in smaller pages, such as 20 rows at a time.
MigrationA safe database upgrade for users who already have older tables and data.
Best effortTry the extra work, but do not break the main operation if that extra work fails.
Bottom line

The plan is now updated and ready for the remaining product choices.

The strongest solution is still early cleanup plus a fresh server check at tap time. The revised plan now includes group resolution, server-side pagination rules, a permanent push fallback, per-type chat rules, an explicit database migration, muted stale history, and the one-shot unavailable-event modal after redirecting to Discover.
