Outcome

Admins now have a Profile → Support Inbox entry that lists existing and new Contact Us and Feedback submissions, prioritizes new urgent safety reports, exposes full details and reply information, and supports New, Reviewed, and Closed workflow states.

Admin identity decision

Email provisions; user ID authorizes.

The scalable solution is a persistent admin_users table keyed by the immutable account users.id. Exact verified account emails in ADMIN_BOOTSTRAP_EMAILS are used only to create the first grants.

Every runtime request checks the signed-in session’s user ID against the database. A client-supplied email, hidden menu, or shared secret never proves admin access.

Authorization and data flow

The production database remains the source of truth. The mobile client can discover access, but sensitive data is released only after both session and database-role checks.

Delivered capabilities

Inbox operations

  • Contact, Feedback, and status segmented filters
  • New urgent safety reports ranked first
  • Pull-to-refresh and opaque cursor pagination
  • Empty, loading, retry, and revoked-access states

Submission detail

  • Full message and creation time
  • Account identity when the submitter still exists
  • Reply preference/address and safe mail composer action
  • New → Reviewed → Closed and reopen controls

Input protection

  • Shared 4,000-character client/server maximum
  • 254-character validated reply email
  • Bounded anonymous rate limiter: five per ten minutes per IP
  • No submission bodies or reply addresses in routine logs

Operations

  • Initial grants through a temporary Fly bootstrap secret
  • Immediate server-side revocation from admin_users
  • 12-month general / reviewed urgent up-to-24-month retention policy
  • No delete API in the first release

API surface

All help-data routes below require a valid session and a persistent admin grant. GET /api/admin-access requires a session and returns only a boolean.

Method Route Purpose
GET /api/admin/help-submissions Filtered, cursor-paginated inbox; defaults to 25 records.
GET /api/admin/help-submissions/:id Full message, reply metadata, status, and nullable submitter.
PUT /api/admin/help-submissions/:id/status Accepts only new, reviewed, or closed.
GET /api/admin-access Lets the signed-in client decide whether to show the Profile entry.

Security properties

What grants access

A valid bearer session whose immutable user ID exists in admin_users. The check happens on every protected request.

What does not grant access

A displayed email, client menu visibility, request body, bootstrap list, shared API key, or direct knowledge of the endpoint.

Expected boundary responses

No session returns 401; signed-in non-admin returns 403; granted admin returns 200.

Data minimization

Submission contents remain in the existing database and protected UI. They are not copied to analytics, push notifications, or default alerts.

Release checklist

The code is ready for integration. Production provisioning should follow this order.

Deploy server first

Apply the schema and protected routes before releasing the client menu.

Set bootstrap emails

Use exact verified account emails in ADMIN_BOOTSTRAP_EMAILS.

Sign in and verify

Each intended admin signs in; confirm the persistent grant and inbox access.

Remove bootstrap secret

The DB grants remain; removing the secret closes automatic provisioning.

Check the boundary

Verify production 401 / 403 / 200 behavior for anonymous, user, and admin.

Release the client

Ship the Profile entry, inbox, detail, and workflow after server verification.
