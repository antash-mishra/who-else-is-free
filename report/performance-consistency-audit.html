Executive Summary

The app's sluggishness is likely caused by several compounding behaviors rather than one isolated bug.

Native screen optimization is disabled, tab screens are mounted eagerly, and custom pagers render all page contents simultaneously. Broad React contexts publish frequently changing state, causing hidden screens and lists to rerender when events or chat data changes.

Interaction inconsistency comes from implementing similar experiences through different primitives. Bottom sheets, buttons, tab controls, haptics, and animations frequently use different timing curves, component APIs, and animation engines.

Primary direction Reduce mounted work first, then reduce context-driven rerenders and network refreshes. Once the app is lighter, standardize the interaction primitives so motion and feedback remain consistent.

Performance Issues

Findings are ordered by expected impact.

All tab screens remain mounted and active

Critical

React Navigation's native screen management remains disabled, and tabs are configured to mount eagerly, so inactive tabs remain attached.

Evidence src/navigation/AppNavigator.tsx:57-60 calls enableScreens(false). The tab options use lazy: false and detachInactiveScreens: false.
Impact Hidden Home, My Events, Messages, and Profile screens remain in memory and continue reacting to context updates.
Optimization Enable lazy tab mounting and revisit native screens or detachment with a transition strategy that does not regress the measured tab-switch frame baseline. Preserve state only for screens that genuinely require it.

Custom pagers mount every page and list simultaneously

Critical

AnimatedPager places every child in an absolute-positioned animated view. Off-screen pages are translated away but remain fully mounted.

Evidence src/components/AnimatedPager.tsx:225-232 maps and renders every child. Home mounts up to three SectionList instances at src/screens/HomeScreen.tsx:378-434. My Events mounts another three at src/screens/MyEventsScreen.tsx:231-290.
Impact Data changes rebuild and reconcile several hidden lists. Images, empty states, refresh controls, and list rows can remain mounted even when users cannot see them.
Optimization Render only the active and adjacent pages, or use react-native-pager-view with lazy page contents. Extract a reusable event-list page to remove the repeated list configuration.

Large contexts create broad rerender cascades

High

The Events and Chat providers expose many unrelated data fields and actions through single context values. Any changing field creates a new value and rerenders every consumer.

Evidence src/context/EventsContext.tsx:754-790 publishes event lists, loading state, errors, and all actions together. src/context/ChatContext.tsx:1226-1261 publishes conversations, active messages, connection state, requests, refresh state, and actions together.
Impact A new chat message can rerender Home, My Events, Profile, Event Details, Messages, Chat Thread, and navigation badges. This is especially expensive because inactive tabs remain mounted.
Optimization Split data and action contexts by update frequency. Suggested boundaries include conversation summaries, active-conversation messages, join requests, event collections, and event actions. A selector-based store is another reasonable option.

Memoization is frequently defeated by unstable props

High

Some rows are wrapped in memo, but parents pass newly created callbacks, arrays, and objects during each render.

Evidence The memoized Home event row receives a new onPress closure from src/screens/HomeScreen.tsx:350-360. My Events follows the same pattern at src/screens/MyEventsScreen.tsx:182-190. Message rows are not memoized and search the complete events array per row at src/screens/MessagesScreen.tsx:91-94.
Optimization Pass stable ID-based handlers, memoize row renderers and separator components, and build an eventById lookup map once instead of calling events.find for every row.

Event Details renders large collections without virtualization

High

Event Details places participant, request, and member collections inside one large ScrollView. Its inline tab pager also renders both pages at all times.

Evidence The main scroll view starts at src/screens/EventDetailsScreen.tsx:1395. Requests and members are rendered with .map() around lines 1657, 1736, 1757, 1813, and 1872. Both tab pages are always rendered at src/screens/EventDetailsScreen.tsx:1636-1774.
Optimization Extract member/request sections and use virtualized lists when collections can grow. Render only the active tab page. Keep the hero/details content separate from high-frequency host management state.

List virtualization is not tuned for repeated heavy rows

Medium

Event lists use images, gradients, blur, masks, and animated press wrappers, but do not provide list tuning such as initialNumToRender, windowSize, maxToRenderPerBatch, or getItemLayout.

Evidence Event rows include image, mask, gradient, and blur work in src/components/EventCard.tsx:58-92. The primary Home and My Events lists do not specify explicit virtualization tuning.
Optimization Profile first, then tune list windows and batch sizes for the target devices. Consider simplifying off-screen card badge effects or applying them only when a badge is present.

Consistency Problems

Similar interactions are implemented through different components and motion systems.

Bottom sheets use at least three transition systems

High

General sheets, Create Event sheets, and navigation-managed sheets have separate implementations.

Evidence
  • BottomSheetModal.tsx:72-100: spring open, timed close, React Native Modal.
  • CreateEventBottomSheet.tsx:59-99: timing-based open and close, inline overlay.
  • AppNavigator.tsx:104-143: navigation-card spring transitions with platform-specific behavior.
Impact Sheets differ in bounce, backdrop fade, keyboard behavior, close timing, mounting, z-index behavior, and Android/iOS behavior. Users experience these differences as inconsistency.
Optimization Create one configurable sheet primitive with documented variants for content height, snap height, keyboard avoidance, navigation presentation, and close behavior. Keep one set of motion tokens.

Buttons use several incompatible interaction patterns

High

The app mixes plain Pressable, pressed-style Pressable, TouchableOpacity, manual Reanimated scale behavior, and ScalePressable.

Evidence ScalePressable.tsx:36-65 defines the shared scale behavior, but Create Event recreates it at CreateEventScreen.tsx:975-1026. Onboarding uses opacity-based touchables at OnboardingScreen.tsx:303-322. Confirmation actions use pressed styles at EventActionConfirm.tsx:38-66.
Optimization Create explicit shared primitives: PrimaryButton, SecondaryButton, IconButton, SelectableChip, and InteractiveRow. Each should own animation, haptic behavior, disabled state, loading state, hit target, and accessibility defaults.

Animation feel is split across engines and local constants

Medium

The app has a useful shared spring file, but many user-facing transitions still define independent timing values and use both React Native Animated and Reanimated.

Evidence Shared presets exist in src/theme/springs.ts. Local constants remain in AnimatedPager.tsx:22-29, CreateEventBottomSheet.tsx:29-30, EventActionBadge.tsx:13-14, and OnboardingScreen.tsx:69-74. React Native Animated is used by Bloom, Splash, Event Action Badge, and parts of Chat Thread.
Optimization Define motion tokens by interaction purpose: press, page change, sheet open, sheet close, fade, toast, and destructive confirmation. Prefer one animation engine for interactive UI motion.

Haptic behavior is manually scattered

Medium

Haptic calls are embedded throughout screens and components, making it easy for equivalent actions to use different feedback or trigger twice.

Evidence The audit found more than 100 direct haptic calls across screens, components, and navigation. For example, Messages triggers haptics on onPressIn while many other rows trigger them on onPress.
Optimization Centralize semantic haptics such as haptics.select(), haptics.confirm(), haptics.destructive(), and haptics.error(). Shared controls should invoke them.

Repeated UI patterns have drifted

Medium

Similar profile avatar editors, event request rows, headers, retry states, and event list pages are implemented repeatedly.

Evidence Onboarding and Edit Profile independently implement avatar selection, camera badges, removal controls, and name inputs. Pending Requests and Event Details independently implement request rows. Home and My Events repeat nearly identical event-list page configuration.
Optimization Extract domain-level shared components, not only visual atoms: AvatarEditor, JoinRequestRow, EventSectionListPage, AsyncState, and AppScreenHeader.

Architecture and Maintainability

Several screens and providers are too large

High

Very large modules combine data fetching, derived state, interaction logic, rendering, and styles. This makes optimization harder because a small state change can rerender a large component tree.

Evidence
  • EventDetailsScreen.tsx: approximately 2,734 lines.
  • ChatContext.tsx: approximately 1,273 lines.
  • CreateEventScreen.tsx: approximately 1,188 lines.
  • ChatThreadScreen.tsx: approximately 875 lines.
  • EventsContext.tsx: approximately 806 lines.
Optimization Split by behavioral ownership. Keep data orchestration in hooks/providers and move stable visual sections into memoized components. Avoid splitting only for line count; split where state update frequency differs.

Derived event and conversation relationships are recalculated in multiple screens

Medium

Home, My Events, Messages, Profile, and Event Details independently derive ownership, joined event IDs, event lookups, and conversation relationships.

Optimization Create normalized lookup selectors such as eventsById, conversationsByEventId, joinedEventIds, and eventRelationshipById. Reuse selectors without placing all derived values into one frequently changing context.

Backend and Network Issues

Conversation summaries have an N+1 query pattern

Critical

The backend queries visible conversations, then hydrates each conversation separately.

Evidence server/repository_chat.go:87-133 loops through conversations and calls hydrateConversationSummary. Each hydration performs participant, former-sender, latest-message, unread-count, and event queries at server/repository_chat.go:825-875.
Impact Request time grows rapidly as conversation count grows. Frequent client refreshes amplify this cost.
Optimization Replace per-conversation hydration with joined or batched queries. Fetch event metadata, latest messages, and unread counts in bulk. Add conversation pagination.

Event listing loads and filters the full event table

High

The events query selects all events, then Go filters past events and blocked hosts in memory.

Evidence server/repository_schema.go:245-250 has no upcoming-event filter or pagination. server/repository_events.go:469-476 filters past events after scanning them. server/repository_events.go:583-614 filters blocked hosts after loading the event list.
Optimization Filter upcoming and blocked-host events in SQL. Add cursor pagination and query parameters for discovery modes where appropriate.

Refreshes are triggered from overlapping lifecycle paths

High

Conversation refreshes happen on provider initialization, socket connection, app foregrounding, screen focus, actions, and polling.

Evidence ChatContext.tsx:730-735 refreshes on user/token changes, ChatContext.tsx:968-974 refreshes on socket open, ChatContext.tsx:1046-1056 refreshes on foregrounding, and MessagesScreen.tsx:162-170 refreshes on focus. Host Event Details additionally polls every five seconds at EventDetailsScreen.tsx:438-477.
Optimization Add a freshness window and in-flight request deduplication. Prefer WebSocket events for live membership and join-request changes. Refresh only when data is stale or a socket event indicates missing details.

The Jest suite has existing regressions

High

The full test run reported 10 failed suites, 28 failed tests, and 962 passed tests.

Impact Performance and shared-component refactors become riskier because failures caused by new changes are harder to distinguish from existing failures.
Optimization Restore a green baseline before major architecture work. Prioritize shared-component and context tests because those modules have the largest blast radius.

Recommended Roadmap

This sequence targets measured user-visible problems first, then reduces architectural causes, and finally consolidates the interaction system. Treat every phase as a separately measured change rather than one large refactor.

The connected Android baseline is now captured in performance-baseline.html. The strongest frontend signals are Discover segment switching at 12 ms median / 31 ms p95, Create open-close at 13 ms median / 17 ms p95, and bottom-tab switching at 11 ms median / 22 ms p95 on a 120 Hz device.

1

Reduce mounted screens, hidden lists, and transition work

Highest frontend priority Measured device impact Moderate navigation risk

The current navigator eagerly mounts and retains tabs, while Home and My Events mount all pager pages. Reduce the amount of work participating in every tab and segment transition before tuning animation constants.

Implementation tasks
  • Enable lazy tab mounting and evaluate inactive-screen detachment or freezing.
  • Mount only the active pager page and, if swipe continuity requires it, one adjacent page.
  • Preserve required state explicitly instead of keeping full hidden trees alive.
  • Profile tab-button springs and pager transitions after mounted work is reduced.
Exit criteria
  • Home and My Events mount no more than active plus adjacent pages.
  • Hidden screens do not rerender during unrelated refreshes.
  • Bottom tabs and segments reach at most 8.33 ms median and below 16.7 ms p95 on the same device.
  • Back navigation and retained form state behave intentionally.
2

Reduce state update reach

High frontend impact Moderate architecture risk Measure render counts

Split providers by update frequency and ownership so a chat message, request update, or event refresh does not invalidate unrelated screens.

Implementation tasks
  • Separate stable action APIs from frequently changing context values.
  • Separate active-thread messages from conversation summaries.
  • Separate event collections, membership state, and request state where update patterns differ.
  • Add memoized normalized selectors such as eventsById and joinedEventIds.
Exit criteria
  • A new chat message does not rerender Home, My Events, or Profile.
  • An event refresh does not rerender unrelated chat-thread content.
  • Render counts are recorded before and after each provider split.
  • No duplicate source of truth is introduced.
3

Fix backend query and refresh amplification

Highest backend priority Measured scale problem API contract risk

Fix the conversation N+1 pattern and overlapping refresh triggers together. Improving only the endpoint or only the client leaves substantial duplicated work.

Implementation tasks
  • Batch latest messages, unread counts, participants, and event metadata.
  • Add conversation pagination and bounded event discovery queries.
  • Add freshness windows and in-flight request deduplication in frontend providers.
  • Replace five-second host polling with WebSocket events plus a stale-data fallback.
Exit criteria
  • Conversation query count becomes constant or near-constant instead of 1 + 4N to 1 + 6N.
  • At 250 conversations, local p95 drops below 15 ms on the same machine.
  • Concurrent refresh requests are deduplicated.
  • Payloads remain bounded as collections grow.
4

Build and migrate shared interaction primitives

Consistency priority Incremental migration Cross-platform QA

Establish one source of truth for equivalent interactions. Shared primitives should own visual states, motion, haptics, disabled behavior, accessibility, and platform differences.

Implementation tasks
  • Define motion tokens for press, tab, pager, sheet, modal, and success transitions.
  • Create semantic haptic helpers instead of direct haptic calls throughout screens.
  • Consolidate primary, secondary, destructive, icon, and row interaction variants.
  • Consolidate bottom-sheet behavior before migrating date, selection, and action sheets.
Exit criteria
  • Equivalent actions have matching motion, haptic, loading, and disabled states.
  • Local timing declarations and direct haptic calls fall substantially.
  • One documented sheet system handles the main variants.
  • Android and iOS interaction checklists pass.
5

Break apart large screens along update boundaries

Maintainability Targeted performance Avoid cosmetic splitting

Start with Event Details and Create Event, but extract only where state ownership or update frequency differs. Smaller files alone do not guarantee fewer renders.

Implementation tasks
  • Move data orchestration into focused hooks with explicit inputs and outputs.
  • Extract stable visual sections into memoized components.
  • Virtualize growing member, request, and event collections.
  • Keep transient form and modal state close to the components that own it.
Exit criteria
  • Updating one section does not rerender unrelated sections.
  • Growing collections remain responsive with realistic seeded data.
  • Extracted modules have focused tests and clear ownership.
  • No behavior or interaction inconsistency is introduced during extraction.
6

Control bundle, asset, and collection growth

Long-term guardrail Release verification Prevent regression

Finish by establishing limits that keep performance stable as features and data grow. Validate with production-like release builds rather than development-build memory alone.

Implementation tasks
  • Remove unused font weights and audit large image assets.
  • Add seeded performance scenarios for events, conversations, members, and requests.
  • Capture Android and iOS release-build startup, memory, and frame baselines.
  • Add bundle, payload, query-count, and interaction-frame checks to release review.
Exit criteria
  • Unused Inter files no longer dominate the web export.
  • Large collections are paginated and have documented limits.
  • Release-build performance targets are recorded for both platforms.
  • Future regressions can be detected against named baseline revisions.
Recommended delivery shape Keep phases 1-3 in separate pull requests with before-and-after measurements. Migrate shared primitives by workflow rather than replacing every button or sheet at once. Do not combine provider splitting, navigation changes, and visual-component migration in the same change because regressions will be difficult to isolate.
